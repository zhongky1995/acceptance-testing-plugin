# 多阶段故障与续办验收

适用于批处理、异步任务、模型或外部服务参与的流程，尤其是单条异常曾导致整批停顿的情况。普通单步改动可沿用原用例。

## 冻结预期

从正常入口沿调用、持久化和交付路径列出本次涉及的阶段。用业务约定确定故障应归属于哪条记录、哪个动作、哪组共享输入或整个事务。决定跨模块行为的规则写回项目有效决策表并关联要求。如整批必须原子提交，整批回滚就是正确预期。规则尚有争议时保留来源和待确认项。

以“批量入账”为例。每行都要能在原任务中观察到下一步。

| 注入位置与条件 | 应受影响的对象 | 其他对象及副作用 |
|---|---|---|
| 校验 B 时缺必填字段 | B 待核，可定位原因 | A、C 的对应版本实际进入入账。已完成的 A 再次续办时新增请求为零 |
| A、B 共用的凭证读取明确失败 | A、B 等待同一凭证 | C 继续入账；另一笔同名凭证不能串用 |
| 入账已提交、响应未知 | 原动作保留未知并等待核对 | 重启后观测到账请求和投递次数，按产品的事务边界决定其他项能否继续 |
| 无合法对象或批次授权已过期 | 按约定结束或停止 | 核对零入账和可见原因，再用合法对照验证正向分支 |

优先回放已脱敏的原请求、回执及同版输入。为各适用阶段选择能区分错误实现的变体，例如缺字段、缺依据、重复或错绑对象、共享依赖、明确失败与结果未知。加正常对照，换对象名称、顺序或题材检查特例。按风险选行；使用随机注入时固定种子，并保存实际命中的位置。

## 执行与签收

1. 在同一冻结版本从正常入口运行整组独立用例。只在要施加故障的依赖边界替换回执。每例使用隔离状态，保存首次失败，已受阻的下游照实记录。先收齐停点，再按共同原因修复。各注入行可独立准备相应前置，避免第一处失败屏蔽后面所有阶段。
2. 从真实消费端读取**所有**应继续对象的标识和版本，从业务账与请求账核对待核原因、同一任务续办，以及已完成、明确未发出和结果未知的动作。检查正常入口、刷新和重复续办后的新增请求与交付数。重用大型只读输入，单例保存紧凑的事件、差异及原件定位。
3. 在修复版本另建一轮，复跑原失败、受影响的好项与保护用例。用受控正例走到最终产物或接收端。若目标还包括自主选材或内容质量，使用同版自然输入，记录首版、每轮意见与修改、最终正文及接收端实际内容。可用无提示错例与正确对照独立审读，检查错判与漏判。
4. 离线结果回答不了且已有授权时，再安排一次聚焦真实验证。按原授权跨轮累计请求和费用，扣除既有占用后以剩余额度设置新轮上限，实际请求前预留。保留未决账，明确重开与续办的区别。插件的单轮账本无法自动归并独立档案。
5. 报告注明测试版本与实际运行版本、真实起点、每段进入/完成数、停点原因、人工操作、接收端、实际费用或上界。正确结束且零产出可以证明空分支；正向产出仍需对应证据。手工选样、回放、分段成功、本机接收与真实用户看到各自对应不同结论。接线拦截或探针故障要和业务拒绝分开记。

## workflow 命令适配器

将决策表的每行作为一个 command case，绑定一个 assurance.samples 输入文件。用例依赖只表达真正的前置。若已约定离线通过后才能实测，在真实用例的 prerequisites 绑定这些必需行。修复后新一轮仍应按累计剩余额度规划。已有同等断言的项目测试也可走现有 native/JUnit 协议。下面是 case 字段节选，完整计划沿用原 schema 1.2。

```json
{
  "sample_ids": ["missing-amount"],
  "workflow_expectation": {
    "stage": "validate", "fault": "missing-amount", "run_id": "batch-7",
    "states": {"A@1": "posted", "B@1": "held", "C@2": "posted"},
    "next_inputs": {"post": ["C@2"]},
    "effects": {"post:A@1": 0, "post:C@2": 1}
  },
  "executor": {
    "kind": "command", "adapter": "workflow", "external_calls": false,
    "argv": ["{python}", "probe.py", "samples/missing-amount.json", "{evidence_dir}"],
    "timeout_seconds": 15, "result_path": "{evidence_dir}/result.json"
  }
}
```

本例从 A 已入账的原批次续办，观察窗口覆盖续办与再次刷新。项目探针读取输入、执行任务，在本次 evidence_dir 保存脱敏原始轨迹，并从实际记录写出 result.json。与预期同名的字段都取自实测；例如 post 消费端实际收到 C@2 才能登记 C@2。返回时另附如下字段：

```json
{
  "sample_id": "missing-amount", "sha256": "实际消费的样本文件摘要",
  "trace_file": "events.json", "locator": "events 2–8；第二次续办后的请求账"
}
```

stage、fault 标明实际命中的故障位置，正常对照可用约定的无故障标识。run_id 核对任务归属；动态 ID 可据原始事件归一为“原批次”与“另开批次”。states 使用可区分版本的标识；next_inputs 按阶段列出实际消费标识，比较时保留重复次数、忽略同阶段排序。effects 的键按逻辑请求或交付对象区分，采用冻结的观察窗口，包含明确要核对的零次动作。所有映射按完整键集比较；空集合用 {} 或 [] 明示。项目可保留逐事件顺序断言处理另有排序要求的场景。

探针正常完成时退出 0，由执行器比较全部预期。流程行为不符判失败；输入或注入位置不符、原始轨迹缺失、探针异常判受阻。report 和 gate 重读结果。探针是否真正经过产品、原始内容是否准确仍需审阅，schema 校验仅能核实记录的一致性。

可运行的[批量入账探针](../tests/fixtures/batch-project/probe.py)及其[回归样例](../tests/test_workflow.py)展示如何从任务事件分别生成原始轨迹和回执。
