# 报告与门禁

原始 session 与证据用于程序计算 report.json 和 report.md。模型在报告之外补充解释，不改写程序判定。

## 门禁优先级

1. 已知必需用例失败 → failed。
2. 其余存在 required 不稳定/受阻/跳过/未执行、证据缺失或版本失效、必需要求未确认/未覆盖、预算超出 → inconclusive。
3. 本轮所有必需要求有范围内门禁通过证据且所有门禁稳定通过 → passed。

非门禁失败仍展示，六个维度独立反映，整体通过只指当前放行规则。没有纳入某维度则 not_assessed，不推断成功。范围外用例不影响当前门禁。

## 负责人说明

说明本轮目标、可交付范围、主要业务影响、阻断原因、未验证范围和需要决定事项。附版本、环境、证据链接、投入、复现和复测。当前报告输出时间为 UTC，用户摘要转为用户所在时区并标明。

涉及业务验收时按 [业务分析与校验](business-validation.md)分别说明业务定义/标准依据、实现符合性和真实业务效果。报告分析可保存在 business-analysis.md，引用要求/用例、实际材料、判断理由与限制；其中尚未纳入 required 用例的意见不冒充程序门禁。缺乏受益者证据时不能用运营者或模型认可外推价值。

## 反馈与缺陷

已复现问题写触发、预期、实际、影响、证据、恢复/处理建议。风险和推测明确标签，不直接归责架构。主观体验保留依据。缺陷优先级依据业务影响，别用总通过率或框架偏好替代。

修复后新轮关联原问题与用例，原轮报告仍保留为历史；重复失败后通过记不稳定，不能抹掉。当前程序没有自动跨轮合并缺陷，代理在业务说明中链接相关档案。

输出的 evidence 维度对应计划中显式证据测试；程序级证据一致性检查另在 gaps 展示，未设置该维度不能把它宣称为“完整审计通过”。
