# 交互检查方法

## 三类结论

实现符合性检查前后端是否兑现约定；需求适配检查能力组合是否支持目标任务；交互与可用性检查用户是否能找到、理解并完成操作。视觉表现按项目约定检查，不能代替任务完成。真实业务效果另需受益者和观察周期相符的证据。

## 在执行前形成判断依据

先复用用户目标、角色、任务规模、设备环境、信息来源和成功终点。按“入口 → 用户决定/动作 → 可见反馈 → 最终结果 → 中断与恢复”写预期路径。

按实际任务选择成熟模式：编辑任务的保存与版本，异步任务的进度与恢复，审批的待办与原因，批量任务的选择与部分失败。逐项记录采用、调整或不适用及理由。参考来源可为项目既有模式或外部资料；不要求每轮调研竞品，也不要求所有项目具备所有模式。

程序要求每条被验收任务检查入口、理解、反馈、完成、预期路径步骤，并判断加载、空态、错误、中断、权限五类状态的适用性。适用才安排用例，不适用写依据并在报告保留。状态内的内容根据任务定义，例如中断可能检查重新打开、草稿保留、取消或接管，不能机械要求每个产品都有撤销。

## 实际检查

- 路径验证：给定路径，验证操作、状态、持久化和最终结果；正常任务与异常恢复各取有风险的代表。
- 认知走查：逐步检查用户是否知道下一步、能否发现正确操作、能否理解其效果、能否从反馈判断进展。复杂或陌生流程优先使用，不对每个普通控件做昂贵评审。
- 目标探索：只给任务目标，不把菜单名称或点击路径当提示。记录实际绕路、误解、不可见状态和补救；实施者已经知道路径时如实标注，不能把同一 Agent 的角色扮演当作无背景用户。
- 真实用户观察：确有对应用户参与时，记录任务、场景、实际行为、必要辅助和结果。用户耗时与 Agent 工具耗时分开；没有通用“少于三次点击”“五秒完成”的自动门槛。
- GUI 按约定设备检查显示、焦点/键盘、遮挡、文案与可访问性。CLI 检查命令发现、参数解释、输出、错误恢复等实际入口。API/后台服务没有人机入口时可有依据地声明交互不适用。

Computer use 只承担操作和取证；它不自动生成可靠的验收标准。自动化可证明路径可执行；评审可提示可用性问题；人类观察可支持相应人群与场景的判断，三者不能混报。

## 成本与复用

小改动只检查受影响任务和状态；需求与界面未变的技术修复可明确选择 focused。冻结方案前复用有效需求与已有路径，命令测试和观察可共用要求。一次原始轨迹可对应多个检查点；新增范围另建一轮。
