# 业务分析与校验

用于业务验收规划、实际检查和解释结果。普通技术修复且业务定义未变时，只复用相关规则和案例；不把每轮验收变成完整产品咨询或新增审批。

## 三类问题分别回答

| 层面 | 校验对象 | 能支持结论的证据 |
|---|---|---|
| 业务定义与标准依据 | 参与者、问题、场景、价值关系、分工、规则与成功口径是否明确、有来源、自洽；关键假设是否得到支持或反证 | 项目有效约定、用户实际选择、真实材料与反例、对应实验；双方认可不能证明实际效果 |
| 实现符合性 | 系统是否按约定处理输入、决策、输出、交接和异常 | 正常入口的实际行为、状态、原文与输出对照、必要数据回查和恢复证据 |
| 真实业务效果 | 受益者是否获得约定价值、责任人负担和成本是否可持续 | 相应受益者的实际任务/采用观察、限定周期运行、维护/成本记录；需符合本轮范围和授权 |

前一层有依据不能替代后一层实测，后一层某次成功也不能消除标准冲突。技术和业务结果都可单独通过或失败。真实效果未纳入本轮时说明未评估，不把所有工程迭代都阻塞在市场验证上。

## 分析与规划

1. 读取项目现行业务定义及其证据，找出提出需求、操作、受益、提供关键输入、承担成本/责任的实际角色。同一个人可兼任，不强加付费或商业化角色。
2. 对相关角色写清期望结果、必要投入、交接和冲突；区分事实、已确认选择、待验解释及未决事项。问题、场景和价值也可能需要通过测试修订，不能直接从现有功能反推正确业务。
3. 将业务约定/假设关联到功能、要求与用例。先写可接受结果及反例，标明来源、配置和样本条件；开放性内容不限定唯一措辞，不临时发明成功阈值。
4. 选择当前最有区分力的正常、反例、边界、冲突与中断场景。规则组合按风险覆盖，不以案例数量或评分表代替判断。
5. 若预期缺乏依据，记录具体冲突或缺口及它影响的结论。已有范围内独立技术用例继续；需要业务方取舍的事项不能由测试者自行确认。

只要方案的任务保存计划即可；实际执行还需范围、权限、时间及费用依据。不得因需要受众证据便自动发消息、招募访谈或调用付费服务。

## 执行中的分析

- 核对实际使用的目标用户、材料、完整配置、运行版本和外部条件。准备缺陷与产品缺陷分别定位，原失败保留。
- 对每项结论保存预期、实际、原始证据定位及判断理由；推演或静态核对明确标注方法，不伪装成已运行的用户任务。
- 观察完整交接和最终可用输出，并记录测试者的手工选材、改稿、重启或补数据。人工完成的部分不能算系统自主能力。
- 模型参与判断或内容生产时，分别检查协议/格式、事实与推理、应用前提、读者/业务价值。原文、专业资料、风格参照分别说明作用，核验实际阶段输入和最终输出。
- 审核意见也需回到证据核实；比较修订前后是否解决原问题、是否新增错误。没有新信息的重试转入诊断，沿用同一问题累计预算。
- 经营者认可、最终受益者有效、愿意付费和经营增长是不同主张，不能互相替代。一条样例通过不能外推稳定日更或全部人群。

## 使用现有数据合同

schema_version 仍为 1.0，不新增程序评分或“业务自动通过”机制。语义分析由执行者依据原始材料进行，内核负责关系、冻结、预算和证据一致性。

| 内容 | 保存方式 |
|---|---|
| 标准与来源 | requirements.statement/sources/status；必要时引用项目规则 ID、段落和版本 |
| 场景及预期 | cases 的 requirement_ids、expected、preconditions、steps、cleanup；使用现有六维中对应维度，如 functional/evidence/cost |
| 推演、内容或用户观察 | observation；先 check，再保存实际核对材料、断言和有证据定位的分析记录，最后 record |
| 范围外假设/新发现 | 冻结前的 feedback 或报告之外的 business-analysis.md；标事实/风险/建议/未知，不改冻结方案 |

`confirmed` 表示该要求/验证标准有确认依据，不表示待验业务假设已经成立。比如“核验最终稿是否保留采用前提”可以是 confirmed，实际结果仍可能 failed。不能把尚未确认的价值阈值写成 confirmed；必需要求为 proposed/conflict 时，现有门禁保持证据不足。

必需业务用例必须在 plan 中 required=true、in_scope=true，并关联必需要求，不能仅写在分析附件里再宣称已被门禁覆盖。不相关用例不要人为设置前置依赖。标准缺失/取证不足用 blocked/not_run 或 requirement 状态保留，已实际观察违背明确预期用 failed。验收中发现新要求应提出新轮，不能通过降低 required 或改预期使本轮通过。

观察附件可以是基于真实材料制作的对照分析，但必须引用实际原文/输出位置，说明观察方法、判断者和限制；它不充当原始运行记录或真实读者反馈。程序只验证其保存与摘要一致性，不验证文字判断本身正确。

## 示例：IP 内容服务

这里只展示设计方法，不把此业务强加给其他项目。

- IP 经营者与读者分别定义成功：经营者希望降低维护负担，读者希望获得有据且适用的判断；具体经营目标仍以项目确认为准。
- 正例检查最终稿是否解释了约定读者场景中的用途；反例使用“总结准确但与读者任务无关”的内容，不能因模型评分高就通过。
- 冲突例检查审核建议是否超出原文，以及改稿后是否保留必要前提；边界例检查材料不足时允许少出/拒绝的规则。
- 自动化例记录是否靠人工补稿才完成。若系统完成但真实读者尚未观察，只能给实现/内容核对结论，读者效果保持未验证。

这些案例的预期、材料与配置需在当前项目中落实后才能执行；示例本身不是通过证据。

## 结果回到哪里

| 发现 | 下一步 |
|---|---|
| 角色、目标、价值关系不成立或冲突 | 回业务定义；保留反证，相关预期重新形成后新轮验证 |
| 选取、拒绝、审核或终止规则缺失 | 回规则与案例；明确优先级和成功/失败边界 |
| 结果明确，但操作或呈现妨碍使用 | 回产品体验；用真实任务复核影响 |
| 约定明确而程序执行违背 | 回技术实现；保留复现并做受影响回归 |
| 样本、目标、配置或测量有误 | 修验收准备；原记录保留，不能冒称产品缺陷已修复 |

原因可能并存，以上分类是定位方向。报告区分实测事实、已证实原因、待诊断假设和建议，不能仅凭现象断言根因。

负责人说明按“层面/角色 → 约定或假设 → 方法与证据 → 结论及限制 → 下一处理环节”组织。report.json 保持确定性门禁来源；分析发现未被门禁表达的重大缺口时，明确门禁覆盖限制并建议新增范围，不能私改本轮结果。经有权角色确认的全局变更回写项目唯一有效约定，失败历史不覆盖。
