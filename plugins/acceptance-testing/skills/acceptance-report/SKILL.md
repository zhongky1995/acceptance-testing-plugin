# 验收报告

读取 [报告规范](../../references/reporting.md) 和 [数据合同](../../references/contracts.md)。使用 `qa.py report` 生成确定性报告，再根据原始证据补充可检查的业务说明。

- 没有 session.json 时，只能报告尚无运行证据，或整理用户提供的既有记录并明确来源，不能伪造一轮执行。
- 程序生成的 report.json 是本轮统计与门禁结果来源。若生成不通过或证据不足，不用文字改成整体通过。
- 读取 report.acceptance 的三类结论、自动检查点、范围与例外；product_accepted=false 时不能宣称整体通过。完整验收使用 `qa.py gate --session-dir RUN` 再核对；focused、历史方案、文档评审和真实用户观察的适用范围分别说明。
- 核对范围、版本、环境、要求来源、每次尝试和证据引用。图表或通过率不能掩盖关键未测要求、零用例、跳过、不稳定或范围内受阻。
- 面向负责人说明能交付什么、主要业务影响、当前阶段结论、需决定事项；技术附件提供复现、环境、预期/实际与原始证据。
- 把事实、静态风险、产品建议与待验证推测分开。新增反馈记录 evidence 来源，不能把框架偏好写成缺陷。
- 功能、稳定性、环境、部署复制、成本与证据完整性分别说明；范围外不是失败，也不是通过。门禁满足不等于市场与商业结果成立。
- 按 [业务分析与校验](../../references/business-validation.md)补充“业务定义/标准依据、实现符合性、真实业务效果”的分项结论，引用要求/用例和证据，说明谁受益、谁判断以及实际人工负担。用例未覆盖的层面标未验证；不以文案覆盖 report.json 门禁，也不自动扩大本轮放行范围。
- 反馈分别指向业务定义、规则、体验、技术执行或验收准备；区分已证实原因与待诊断假设，给出回到哪个环节、需补何种证据。必要全局规则由有权角色更新项目唯一有效文档，原轮标准与报告不改写。
- 标明实际时间、费用上界与已知费用；模型使用未计量则标未知，不算成零。
- 原版本重试与代码修复后的新版本复测分别关联；跨轮引用结果注明历史验证，本版不会自动将旧结果提升为当前门禁通过。

交付 report.md、report.json、必要业务说明与复测清单，保留已有原始报告。需要进一步执行时交给总控在本轮目标和预算内安排。
