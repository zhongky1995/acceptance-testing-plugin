# 交互与可用性验收

读取 [交互检查方法](../../references/interaction.md) 与 [程序验收协议](../../references/acceptance-protocol.md)。使用宿主已有浏览器、computer use、终端或人工观察能力；不自动安装框架。

先核对本轮用户任务、角色、入口、预期路径、可见反馈、适用状态与模式取舍。标准来自用户目标和已确认约定；同类产品和通用原则用于发现缺口，不直接升级为新需求。方案未冻结前通过规划补齐 `acceptance.journeys` 和对应 `assessment` 用例。

1. 用 `qa.py readiness` 查看程序推导的检查点。漏项、未知适用性、没有证据的“后续再测”不能当作通过。限定范围来自本轮目标，不能为了变绿而缩小范围。
2. 执行前用 `qa.py check` 获取本次 `check_id` 和观察模板。必需需求基线未完成时先核对基线；无关技术用例可继续。check 返回 allowed 才执行对应操作。
3. 从约定用户入口实际走查。分别使用有步骤的路径验证、只给目标的探索；后者记录是否接触实现知识、辅助说明及人工补救，不假装不知情。后台仅可辅助核验结果，不能绕过坏掉的界面完成任务。
4. 记录每个检查点的预期、实际、断言和证据文件索引，保存真实操作轨迹、可见结果、异常及恢复；以 `qa.py record` 导入。可以复用同一条真实轨迹证明多个点，不必为每个点重新点击。
5. 调用 `qa.py report`，分别说明实际路径能否完成、可理解性风险及真实用户证据。Agent 走查标 `actor_kind=agent`；只在实际观察人类操作时使用 `human_observation`，不推断全部用户会用。

已运行的自动化浏览器轨迹也可导入为观察；普通 UI 回归仍可作为实现层命令用例。对语义与任务匹配的判断须可复核，不从截图存在、HTTP 200 或点击次数少推定体验合理。

发现归属：约定明确而控件失效回实现；必要能力缺失回需求适配；入口、状态或路径阻碍任务回交互设计。记录事实与原因假设，调整标准/路径时新建轮次，不改原轮获得通过。
