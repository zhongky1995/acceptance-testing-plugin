# 业务验收

读取 [业务检查](../../references/business.md)、[工具适配](../../references/adapters.md) 和 [数据合同](../../references/contracts.md)。从已确认的规则和任务终点确定正确结果，不从页面现状反推需求。

按 [业务分析与校验](../../references/business-validation.md)分别检查标准依据、实现符合性及本轮纳入的业务效果。对照实际输入、配置、输出和原始依据执行断言；分析意见需引用可检查材料，文件存在或模型 pass 不证明语义成立。

按 [程序验收协议](../../references/acceptance-protocol.md)将任务的目标匹配和完整工作适配登记为 need_fit 检查；经有依据的基线核对后，再执行 [交互验收](../acceptance-experience/SKILL.md)。接口与业务规则通过不能填补交互层面。

- 多角色场景分别核验各方输出与负担，记录人工补救；不能把运营者满意等同最终受益者有用。
- AI 业务分别核验事实/推理、场景适用与读者价值；检查审核建议是否有据、修订是否实际解决问题及是否引入新错误。规则写入提示词不等于执行有效。
- 发现问题时先区分业务定义、规则、体验、技术执行和验收准备，保留诊断依据与不确定性。明确标准而实现违背才据证据判实现缺陷；业务假设被反证不能一律归为代码错误。

- 技术测试结果能覆盖同一业务要求时复用已有执行证据，仍检查该断言实际证明的内容。
- 端到端用例从约定入口执行。登录、创建、提交、审批、导出等必须核验最终结果及必要的数据/角色状态，不能只看成功提示。
- 稳定流程优先用宿主已有浏览器自动化；探索任务用实际可用的 computer use。根据当前工具文档操作，不虚构截图、点击或能力。
- 浏览器/模型能力不足时标受阻或安排人工完成，不通过后台绕路宣布用户流程通过。后台可用于辅助核验，报告说明核验方法。
- 根据风险覆盖边界、条件组合、无效状态、权限、重复操作、刷新/重进、中断、失败恢复、批量部分成功。选测规则见 business.md。
- 宿主操作前用 `qa.py check --plan PLAN --session-dir RUN --case ID` 核对前置与预算，保留 check_id；实际工具调用仍由宿主权限控制。每个观察保存真实证据、逐检查点的预期/实际断言及证据索引、宿主/模型及时间费用记录，用 `qa.py record` 导入。环境哈希和项目快照必须与执行时一致。临时日志或截图来自真实工具输出，禁止用生成内容冒充证据。
- 主观体验评价单列依据；AI 的可用性意见不替代业务负责人对工作适配性的最终验收。
- 使用测试账号/数据和已授权的外部服务；重复、支付、发消息等实际副作用严格遵循本轮授权与预算。

输出任务结果、业务影响、证据和适用限制；模型对证据的判断也需可检查，证据文件存在不能独立证明业务结论。
