# 测试规划

读取 [共享约定](../../references/workflow.md)、[场景规则](../../profiles.json) 和 [数据合同](../../references/contracts.md)。先使用 `qa.py init` 发现项目，再读取重点材料；发现记录不能替代内容分析。

## 形成基线

- 提取角色、核心业务对象、任务终点、规则、状态、失败恢复和关键非功能要求。来源记录具体文档位置或用户的实际确认；当前实现只能证明现状。
- 冲突标 `conflict`，缺乏确认的建议标 `proposed`；不把推断升级为已确认。关键未知影响某一结论时保留缺口，其余工作继续。
- 分析实际改动与依赖关系；影响无法确定时扩大必要回归。本地优先复用有效环境及既有测试，不默认冷安装、完整压测或恢复演练。
- 每项本轮必需要求至少安排一个范围内门禁用例；用例记录清晰预期、前置、输入、步骤、检查及清理方式。不能以测试通过率代替关键要求覆盖。

## 业务分析与校验基线

涉及业务验收时读取 [业务分析与校验](../../references/business-validation.md)。复用项目业务定义和正反案例，区分需求提出者、操作者、受益者及实际相关的投入/责任承担者，核对各方价值、分工、规则冲突和成功终点。角色、问题和价值本身可以是待验假设，不强行收敛成单一用户画像。

建立“业务约定/假设 → 能力/功能 → 要求 → 用例 → 证据”的关联；分别安排标准依据检查、实现符合性和范围内的真实效果验证。使用现有 requirements/cases/observation 字段，不创造执行内核不支持的状态或评分。业务假设的验证方案获确认不代表假设为真；缺乏已确认标准的必需要求保持 proposed/conflict，不能降为非门禁以制造通过。

按风险选择正常、反例、边界、角色/规则冲突和中断场景，并在执行前写预期。取证对象、实际目标/配置、材料完整性、人工干预和观察周期需与主张匹配；最终用户效果不能由经营者或模型认可替代。无法取得的必要证据标明缺口，不默认对外联系或增加付费调用。

## 选择用例与投入

- 按 [技术检查](../../references/technical.md) 和 [业务检查](../../references/business.md) 的适用项设计测试；涉及新环境、私有化、商业交付时才读取 [交付评估](../../references/delivery.md)。
- 先复用已有用例并检查其断言，再补缺口。业务规则可以跨接口与界面验证，共用要求/用例编号，避免重复整套测试。
- 对稳定且便宜的自动测试优先执行；高成本专项须有明确目标、环境和指标，数值来自目标，缺少时不虚构。
- 方案明确 `in_scope` 与 `required`。范围外不影响本轮门禁；范围内未执行是证据缺口。非门禁发现也必须报告。
- `exit` 只用于有明确结果的构建/静态命令检查，测试套件选择 `junit`、`playwright` 或 `native`，不能用退出码掩盖零用例/跳过。
- 环境记录宿主、模型（可获得时）、工具/浏览器/服务版本及关键非敏感配置。外部服务或模型未核验时注明限制。方案效力依赖这些事实，不只依赖文件快照。
- 说明预计时间、安装需求、外部调用费用上界与重试数；已有授权足够时直接推进。`allow_install=false` 是本地起点，第三方预检也先读后补。

## 交付

输出可读方案概览并保存 `plan.json`。运行 `qa.py validate`；只要方案时停止于该产物，不把校验成功称为测试通过。拟沿用历史证据时根据变更核查版本与环境，本版没有自动跨轮复用门禁，必要用例应重跑或重新记录核验依据。
