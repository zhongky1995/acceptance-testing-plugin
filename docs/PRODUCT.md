# 产品范围与使用原则

## 要解决的问题

非技术负责人通过 AI 开发产品时，需要依据已确认的产品要求掌握验收节奏。插件把产品与架构材料转成可以实际执行的测试方案，再以证据说明哪里通过、哪里失败、哪里仍然不知道。

## 三种主要场景

| 场景 | 默认策略 | 何时扩大检查 |
|---|---|---|
| 本地持续开发 | 复用当前环境，验证本轮变化及关键冒烟/回归 | 变化涉及关键角色、数据、协议或风险 |
| 接手第三方交付 | 先只读核对材料、依赖、运行条件与已有测试 | 缺少必要条件时给出最小补齐方案 |
| 目标环境交付 | 按真实交付承诺增加部署与运维验证 | 承诺私有化、升级恢复、多客户复制或服务指标 |

单纯请求「启动让我试用」只启动环境并检查可访问性。只要方案时不执行测试。未说明的生产操作、收费调用、业务代码修复和发布不因验收任务自动获得授权。

## 测试能力与选择

技术目录涵盖构建/静态、单元/组件、集成、接口契约、数据、权限安全、性能容量、异常恢复，以及被测产品涉及模型时的 AI 评测。业务目录涵盖角色、规则、完整用户任务、异常分支和真实结果。交付目录涵盖环境适配、依赖必要性、复制部署、稳定性、维护负担与成本。

目录是选择范围，不是每次都执行的清单。冒烟是启动后检查关键可用性的短路径；回归按变化和风险选择；门禁是本轮必须满足的标准与证据条件。覆盖率和总通过率不能替代关键业务要求。

业务分析分别检查业务定义/标准依据、实现符合性和范围内的真实业务效果。角色、场景、各方价值与分工可能需要通过案例或实测修订；经营者认可不等于最终受益者有效。问题回到业务定义、规则、体验、技术或验收准备的相应环节，不全部归成代码缺陷。详细方法见[业务分析与校验](../plugins/acceptance-testing/references/business-validation.md)。

此能力由技能指导分析，复用现有要求、用例和观察记录；不新增语义评分内核，不自动访谈受众或调用模型。必要业务检查需进入本轮门禁用例，分析附件不能代替门禁或原始证据。

## 插件组成

七个技能负责总控、规划、技术、业务、交互、交付和报告。共用参考材料、场景配置与 Python 执行工具。默认一个 Agent 按需读取；不把多 Agent、独立模型 API、数据库或新的浏览器服务作为基础依赖。

不同宿主的差别主要是可用工具：优先使用项目已有测试与命令；稳定流程可用已有浏览器自动化；探索性业务任务可用宿主 computer use；工具不足时说明受阻条件，必要时导入人工观察与原始证据。不能用接口绕过失败的用户入口后宣称用户任务通过。

## 可信结论

- 已确认要求是验收基线；代码当前行为不能自己证明正确。缺失、冲突、建议和实现偏差分别记录。
- 方案在执行前冻结，结果绑定版本与环境。修复、更换标准或环境后新建轮次。
- 执行记录保留首次失败、每次尝试及原始证据；失败后重试成功仍显示不稳定。
- 零测试、跳过、未执行、缺证据和关键要求未覆盖不能算通过。
- 对负责人给出本轮结论、缺陷影响、方案反馈、未测范围与下一轮建议；技术细节保留为附件。

## 投入与商业交付边界

按风险确定预算，限制累计执行时间、尝试次数及声明的外部费用。优先复用已有环境；没有交付目标时不默认做全新安装、多系统矩阵或昂贵专项。

成本同时记录费用上界、已知实际费用与未知项。宿主推理费用无法获取时明确未知。交付可复制性、环境依赖和维护负担需要对应实测或估算，不能仅凭技术方案通行就认定适合商业化。

当前版本的实测范围及限制见 [验证说明](VERIFICATION.md)。

## 交互与程序防漏

实现、需求适配、交互各自形成结论。前端控件失效属于实现，必要能力缺失属于需求适配，入口/反馈/动线妨碍任务属于交互；外观精美不能代替这三类判断。

schema 1.1 根据本轮任务、路径与适用状态推导必要检查，形成先行基线、实际执行、逐点证据和最终门禁。局部检查可以缩小投入，但必须保留范围依据，不能声称整体通过。约束作用于程序的调用和产出，不对 Agent 的主观判断或外部绕过提供绝对保证。
